### Algorithms and Data Structures 

My understanding of algorithms and data structures has developed from selecting a structure because it works to evaluating why it is appropriate for the application’s scale and behavior. In the capstone artifact, I created a SceneObjectRegistry that combines a vector with an unordered map. The vector maintains ownership and predictable traversal order, while the unordered map connects stable string identifiers to vector positions for expected constant-time lookup. This hybrid structure avoids maintaining duplicate object copies while supporting both ordered rendering and efficient direct access. 

I also implemented object selection through world-space ray casting. A center-screen input ray is transformed from clip space through eye space and into world space by using inverse projection and view matrices. Each object’s local bounding box is transformed into a conservative world-space axis-aligned bounding box, and the slab method determines whether the ray intersects it. The selection algorithm evaluates positive intersections and retains the nearest valid object. For a scene containing five selectable objects, a linear O(n) pass provides clear, testable behavior without the added maintenance cost of an octree or bounding-volume hierarchy. If the scene grew substantially, spatial partitioning would become a reasonable next step. My instructor specifically recognized this complexity analysis as evidence of sound algorithmic judgment. 

Eight automated tests verify registry insertion, lookup, invalid and duplicate identifiers, transformed bounds, hits, misses, and nearest-object selection independently of the graphics runtime. Separating this logic from OpenGL made defects easier to isolate and showed me how testability should influence architecture. The result demonstrates that I can design and evaluate a computing solution using algorithmic principles while managing the trade-off between performance, clarity, and current requirements. 

### Software Engineering and Databases 

Software engineering coursework taught me to see maintainability, resource ownership, failure behavior, and reproducibility as features rather than optional cleanup. The original CS 330 artifact rendered a recognizable desktop scene, but it contained repeated setup logic, fragile texture handling, limited validation, inconsistent resource cleanup, and tightly connected rendering behavior. For the software design and engineering enhancement, I improved initialization, made scene preparation repeatable, centralized texture definitions into a data-driven configuration, corrected OpenGL cleanup, strengthened missing-resource behavior, improved documentation, and revised the shader and lighting calculations. I chose incremental refactoring instead of rewriting the entire application. This preserved working behavior, reduced regression risk, and made the differences between the original and enhanced versions easier to evaluate. My instructor identified that choice as evidence of good engineering judgment. 

The database enhancement changed the application from an in-memory scene into a persistent system. I designed a normalized SQLite schema for scenes and scene objects, used primary and foreign keys to represent relationships, added constraints and indexing, and implemented parameterized create, read, update, list, and delete operations. Scene updates occur inside transactions so a failure does not destroy the last valid saved state. I stored the sixteen values of each transformation matrix in explicit numeric columns rather than an opaque binary object or a string representation. Although this creates a wider table, it preserves numeric types, avoids text parsing, and makes stored values inspectable during review. 

Ten automated database tests exercise schema initialization, saving, loading, updating, listing, deletion, validation, missing-scene behavior, transformation persistence, cascading relationships, and injection-style input. Parameterized statements ensure that quote-heavy input is treated as data instead of executable SQL. The database was tested independently from the graphics runtime so that a driver, shader, or windowing failure could not hide a persistence defect. I also addressed a Win32 calling-convention mismatch in the runtime SQLite loader, reinforcing that deployment and dependency behavior are part of software quality. 

Instructor feedback identified concurrency analysis as an area for continued growth. The current use of SQLite full-mutex mode, transactions, and a busy timeout is appropriate for a single-user desktop application, but a multi-user version would require deeper evaluation of SQLite locking and simultaneous writes. A future design might use a client-server database, application-level conflict handling, or versioned records. This feedback helped me distinguish between a design that is correct for the present requirements and one that would remain appropriate after the operating context changes. 

### Security Mindset 

My security coursework and capstone experience changed security from a final checklist into a design perspective. I now ask what input can be malformed, what resource can fail, what data must be trusted, what permissions are necessary, and how the system should respond without exposing or corrupting information. In the capstone, this mindset appears in validation of identifiers, bounds, matrices, texture capacity, database paths, and stored records. It also appears in parameterized SQL, transactional updates, controlled error messages, predictable cleanup, and the decision not to trust persisted data simply because the application created it. 

Security also influenced how I packaged the project. The repository separates source artifacts from generated executables and development caches, preserves the original version for comparison, documents external dependencies, and provides testing evidence. These practices improve reviewability and reduce the likelihood that unnecessary or environment-specific files will be distributed. As I continue into software engineering, the cybersecurity certificate will help me contribute to secure coding, code review, risk analysis, and defense-in-depth decisions while continuing to build usable applications. 

### Portfolio Integration and Professional Value 

The artifacts in this ePortfolio are most effective when viewed as stages of one engineering story. The original CS 330 project establishes the starting point: a C++ and OpenGL desktop scene using primitive meshes, textures, materials, lighting, camera navigation, and shaders. The first enhancement improves the application’s structure, reliability, resource handling, documentation, and visual behavior. The second adds searchable scene-object data, geometric intersection algorithms, object selection, complexity analysis, and eight independent tests. The third adds a relational database, validated and parameterized CRUD operations, transactions, persistent transformations, and ten additional tests. 

Together, the enhancements demonstrate more than three isolated technical requirements. They show that I can assess an existing codebase, preserve useful behavior, identify weaknesses, design improvements, implement them across connected components, verify the results, respond to feedback, and explain the trade-offs. The progression from static rendering to an interactive and persistent application also demonstrates how software engineering, algorithms, databases, and security depend on one another. The registry’s stable identifiers support both object selection and database persistence; validation protects both in-memory invariants and stored data; and modular design allows algorithms and database behavior to be tested without launching the graphics application. 

This portfolio represents the professional I am becoming: a software engineer who is comfortable learning across disciplines, communicates decisions clearly, and treats reliability and security as part of delivering value. My experiences in programming, mobile development, databases, graphics, embedded systems, artificial intelligence, and cybersecurity have given me a broad technical foundation. My mentoring and professional experiences have reinforced the importance of listening, adapting communication, and considering the people who will use the system. I am prepared to contribute to a development team, continue learning new technologies, and build software that is maintainable, secure, and meaningful to the communities it serves.
